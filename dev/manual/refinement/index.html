Refining the graph

The graph decides how good the certificate can be and how much it costs, and a generic graph pays for nodes everywhere: the De Bruijn graph of order $k$ has $M^k$ nodes whatever the system, and on the running example, orders 3 and 4 double the nodes for no better bound (see Choosing a graph). Refinement builds the graph from the certificate instead: it solves, reads where the certificate is tight, lifts the graph there, and solves again. An outer loop searches over graphs, and on each graph certify computes the best certificate.

The code on this page uses the running example of Systems and problems: system, and problem = PCC.StabilityProblem(system), solved with Clarabel.

In one call

refine starts from the one-node graph and runs the loop:

trace = PCC.refine(PCC.QuadraticTemplate(), problem; optimizer = Clarabel.Optimizer)
PCC.rates(trace), PCC.n_nodes.(PCC.graphs(trace)), PCC.n_edges.(PCC.graphs(trace))
([0.9586944580078125, 0.871798038482666, 0.8688297271728516], [1, 2, 3], [2, 4, 6])

In two steps, the rate drops from about $0.959$ to $0.869$ with 3 nodes and 6 edges, where the De Bruijn hierarchy needs order 2, with 4 nodes and 8 edges, for the same bound. refine(template, graph, problem) starts from your graph instead. Refinement runs on stability only.

How a step works

A step reads the tight edges of the certificate, those whose edge inequality is active (see Reading a certificate). Two results of (Ninite and Jungers, 2026) say where to lift:

  • Only the tight edges matter. The tight edges alone give the same rate (Prop. 1): they hold the rate up, so the graph is lifted where they are.
  • A node with a single tight outgoing edge is not worth splitting. Splitting it cannot lower the rate (Prop. 3); a node with two or more may.

The default algorithm, TightestNodeSplitting, follows Algorithm 1 of (Ninite and Jungers, 2026): it splits the node with the most tight outgoing edges into one copy per outgoing edge, with OutSplitLift, and solves again. From the one-node graph, the first step gives the dual De Bruijn graph of order 1. When no node has two tight outgoing edges, the rate is the joint spectral radius (Thm. 4), and the run stops.

Every step is a lift that needs nothing from the template (see Lifts), so the rate never increases, up to the bisection tolerance, and the lifted graph is path-complete without a new check.

Another algorithm

refine takes an algorithm keyword. BestOfTightEdgeLifts follows Example 2 of (Athanasopoulos and Jungers, 2019): it applies each split and each product at every tight edge, solves every candidate graph, and keeps the one with the lowest rate. A step costs one solve per candidate.

When it stops

status(trace) says why the run stopped:

StatusThe run stopped because
OPTIMALthe rate is proved equal to the joint spectral radius
STALLEDstall_max steps in a row did not lower the rate by rtol
DEPTH_REACHEDdepth_max graphs were visited
STOPPEDthe stop predicate held, for example c -> c.rate < 1
EXHAUSTEDthe algorithm found no next graph
PCC.status(trace)
OPTIMAL::RefinementStatus = 0

On the running example, the run stops with OPTIMAL: on its three nodes, every node has one tight outgoing edge, so the rate $0.869$ is the joint spectral radius of the system, reached and proved in two steps.

The trace

The RefinementTrace keeps every step: certificates, graphs, rates, and steps, each step a Lifted graph with the origins of its nodes.

Tolerances

Three tolerances drive the run: rtol, the bisection tolerance of each solve; atol, below which a slack counts as tight, at least ten times rtol; and gap_tol, the gap between the rate and its lower bound at which the run stops.
