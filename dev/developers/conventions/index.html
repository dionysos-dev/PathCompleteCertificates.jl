Conventions

The rules for code under src/. The Julia style guide is the authority on anything not said here.

Two axes

A certificate is a labelled graph, a function $V_s$ from a template at each node and one inequality along each edge, and only the inequality changes between problems:

ProblemEdge inequality on $(s, d, i)$
Stability$V_d(A_i x) \le \gamma^{p}\, V_s(x)$
Safety$B_d(A_i x) \le B_s(x)$
Optimal control$x^\top Q x + u^\top R u + V_d(A_i x + B_i u) \le V_s(x)$

Templates and problems are therefore two independent type hierarchies. The template, src/templates/, says what the node functions are, and the problem, src/problems/, says what the edge inequality is. A template supplies primitives, a problem composes them, and neither names the other.

# Template axis: one file per template, answering all of it.
add_function_variables!(model, template, dim, node)        # the node function V_s, well defined
add_decrease!(model, template, V_src, V_dst, map; scale = 1)
                                                           # scale·V_src(x) − V_dst(map·x) ≥ 0
decrease_slack(template, V_src, V_dst, map; scale = 1)     # the same, read off a solution; 0 when tight
add_normalization!(model, template, V)                     # excludes V ≡ 0
homogeneity_degree(template)                               # p: V(cx) = cᵖ V(x)
solution_value(template, V)                                # variables -> a callable node function
is_applicable(template, system)                            # default true; does the template apply at all?
is_closed_under(template, ::Operation, system)             # default false; which lifts are valid
reindex(template, origins)                                 # per-node data follows a refined graph
has_dual(template), dual(template), dual(template, V)      # the dual norms, when they exist

# Problem axis: one file per problem, composing the above.
node_value(template, problem, V, x)                           # V(x), or V([x; 1]) for safety
optimization_model(template, graph, problem; optimizer, ...)   # build, do not solve
certify(template, graph, problem; optimizer, ...)             # build, solve, extract
best_certificate, objective, optimality_gap, edge_slacks       # what refine reads

# The common function: each node value from the problem (node_value), their combination
# from the graph alone (graphs/observer.jl); the public method is in problems/certificate.jl.
common(template, graph, problem, Vs, x)

Every primitive is public, since a user implements it. Problems express their edge inequality through add_decrease!: quantifying an inequality over every $x$ needs a cone that depends only on the template, so stability's edge condition is one call with scale = γᵖ. Optimal control is the exception. Its inequality is convex only after the substitution $S = P^{-1}$, $Y = KS$, so it cannot be written against V_src and V_dst; it works on the quadratic template's variables directly, and a comment in the code says so. Each problem writes its edge condition once, in a private _edge_decrease that both builds the model and measures the slacks.

A template is an instance, never a type: ParallelFacesPolyhedralTemplate carries a matrix per node, and ::Type{T} has nowhere to put it. An AbstractTemplate is the family; the fitted node function is what solution_value returns.

Each problem has its own certificate type. The shared fields live once in CertificateData; what the problem certifies is a typed field of its own, rate, margin or gains.

A new template, problem, lift or refinement algorithm is one file in the catalogue/ of its directory, and touches nothing else. Every directory with an interface has that shape: the interface at the top, one file per inhabitant under catalogue/, named after the type without the directory's suffix.

Lifts and refinement algorithms

A lift is an operation on a graph; refine is an algorithm that applies lifts. A lift maps a path-complete graph to a path-complete graph no worse for every template closed under its requirements. The same lift can be a step of a refinement algorithm and a test of compare, where a simulation of $H$ by the lifted $G$ proves $G \le_V H$.

# src/lifts/operations.jl: what a template is closed under and a lift requires.
Addition(), Maximum(), Minimum(), Composition(), InverseComposition()

# A lift, src/lifts/catalogue/: the forms its definition gives it.
lift(L, graph)                               # a Lifted: the graph and what each node stands for
lift(L, graph, edges)                        # at each edge, for the splits and products
lift(L, graph, node)                         # at a node, for the splits
requirements(L)                              # the operations it needs; () by default
simulation(L, G, H; optimizer)               # inherited; overridden where the theory decides cheaper
is_valid(L, template, system)                # written once against the two
dual(L)                                      # a DualLift, applied on the dual graph
compare(G, H; templates, system, optimizer)  # the entry point of comparison

# A refinement algorithm, src/refinements/catalogue/: one method to write.
next_graph(algorithm, certificate; atol, solve) # the next Lifted graph, or nothing
initial_graph(algorithm, system)             # where it starts; common_graph by default
refine(template, graph, problem; algorithm)  # the entry point: the loop

What a lift supports is the methods it has, never a flag. Validity is read from the closures a template declares, never by dispatching on its concrete type, which would need a method per pair. A lift valid on a template that is not closed under its requirements is read through the dual template: the min lift is valid on the linear copositive template because its dual is closed under max. The min, max and sum lifts are never built to decide an order: a relation decides the first two and a linear program the third. An algorithm chooses its candidates and how to select among them; the loop owns solving, the stopping rules and the trace.

The graph layer

The certificate graph is a HybridSystems.GraphAutomaton, or a WordGraph when edges read words. Constrained switching is not supported: n_modes refuses a system whose automaton is not a OneStateAutomaton. graphs/queries.jl is the only file that touches the backing store, so this stays empty:

grep -rn "_HS\.\(GraphAutomaton\|add_transition!\|Σ\)" src | grep -v queries

Build graphs with empty_graph, WordGraph or _empty_like, which picks the kind by dispatch; a constructor returning either kind by keyword is not type-stable, and Base.return_types(de_bruijn, (Int, Int)) must stay one concrete type.

There are three predicates. is_path_complete, every admissible sequence readable as a path, is the soundness question, decided by the subset construction; is_complete and is_co_complete are sufficient only, and decide the form of the common function. Always ask with the system's modes, 1:n_modes(system): is_path_complete(graph) alone asks about the modes the graph happens to use. Path-completeness is PSPACE-complete, so it is checked once per solve, and path_complete = false waives it; never make that the default. Index adjacency with _successors and _predecessors rather than calling the star queries in a loop.

A word graph is sound for stability only; safety, optimal control and common throw on one and name expanded_form.

Naming

  • Types CamelCase, functions snakecase, constants `UPPERCASE, non-public names_`-prefixed.
  • Mutating functions end in !; predicates are is_*.
  • No get_, compute_, build_ or generate_ prefixes; name a function after what it returns.
  • No acronyms in public names.
  • One word per concept, and the papers' word when one exists: common, valid, simulation, tight, common_graph, alphabet.
  • Node functions are callable: V(x).
  • No Base.show methods, and no utils.jl.

Types and signatures

  • Argument order follows the style guide, which is why the template comes first in certify(template, graph, problem).
  • No unused static parameters: f(x::Real), not f(x::T) where {T <: Real}.
  • No type piracy; Aqua fails the build on it.
  • Methods over field access: alphabet(g), not g.alphabet.
  • Never hard-code Float64 in a signature; a certificate may have to be exact.
